## 四、设计漏洞与逻辑缺陷

### 4.1 设计/逻辑问题 1：fix-duplicate-doctor-table.sh 的验收前置条件

- **现象**：测试验收文档 F2.2、4.5、4.6、六节多处要求验收时执行 `bash scripts/fix-duplicate-doctor-table.sh` 或等价步骤。  
- **问题**：《项目分析与结构说明》将 `scripts/fix-duplicate-doctor-table.sh` 列为 **缺失项（P2）**，若该脚本未实现，则验收说明会产生「执行不存在的脚本」的逻辑矛盾。  
- **建议**：在测试验收文档中明确「若项目中不存在 fix-duplicate-doctor-table.sh，则通过 phpMyAdmin 或 MySQL 客户端检查 qa_healthcare 下仅有一张小写 doctor 表」。已在《测试验收文档》中增加【评审意见】及可选表述。

### 4.2 设计/逻辑问题 2：api.md 与「全部 API」的边界

- **现象**：README 要求「对 qa-service-user 服务中的**所有** API 进行说明」；技术实现 3.3 列出 GET/POST/OPTIONS /api/test/cors；docs/api.md 已覆盖 /api/doctors 与 /api/test/cors（GET/POST/OPTIONS）。  
- **问题**：若后续新增其他 API（如健康检查、Actuator 端点），容易遗漏在 api.md 中更新，「全部 API」的维护责任未在文档中写明。  
- **建议**：在《技术实现文档》或《测试验收文档》中增加一句：「凡 qa-service-user 对外暴露的 HTTP API，均应在 docs/api.md 中登记并含测试说明或引用 API_TEST.md」。已在《技术实现文档》3.3 增加【评审意见】。

### 4.3 设计/逻辑问题 3：首页「统计与开放诊室」数据源与 AC1.7 的闭环

- **现象**：AC1.7 要求「首页统计数字与开放诊室列表与数据源（GET /api/doctors 或与之一致的后端）一致」；技术实现 4.2 推荐首页同样调用 GET /api/doctors。  
- **问题**：若前端首页仍从本地 JSON 或其它来源取数，则与 AC1.7 不符，且需求未显式写「首页医生相关数据必须来自 GET /api/doctors」。  
- **建议**：在需求分析文档 AC1.7 中明确「数据源指 GET /api/doctors 或与之一致的后端接口」，避免歧义。已在《需求分析文档》AC1.7 处增加【评审意见】。
