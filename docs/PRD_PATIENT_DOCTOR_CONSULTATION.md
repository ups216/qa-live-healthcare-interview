## 2. 背景与问题

### 2.1 背景

- 当前项目是一个在线问诊演示系统，前端包含首页、医生列表、患者问诊、医生登录、医生诊室等页面。
- 后端已拆分为两个服务：
  - `qa-service-user`：负责医生与患者用户相关能力，端口 `8080`
  - `qa-service-question`：负责问诊问题相关能力，端口 `8081`
- 前端基于 Vite 运行，开发端口需避开两个后端服务端口。
- 项目初始化数据来源于前端目录下的 3 个 JSON 文件，运行时真实数据源为 MySQL。

### 2.2 当前问题

- 患者和医生需要完成从登录到业务操作的完整闭环，而不是依赖前端本地模拟逻辑。
- 患者提问、医生回复、问题状态流转需要由后端接口统一承接。
- 初始化数据需要在数据库中完成首次导入，但不能每次重启重复覆盖。
- 页面刷新后需要保留登录态，否则用户体验中断。
- 项目需要一份正式 PRD，用于后续迭代、联调、测试和交付。

## 3. 目标与范围

### 3.1 需求目标

- 实现患者注册、登录、提问、查看历史问诊记录的完整流程。
- 实现医生登录、查看分配问题、回复问题、标记已答的完整流程。
- 将医生、患者、问诊数据统一落库到 MySQL，并通过后端接口提供服务。
- 保证页面刷新后医生和患者登录态仍可恢复。

### 3.2 成功标准

- 患者可成功注册或登录，并向指定医生提交问题。
- 医生可成功登录并在诊室中看到属于自己的待处理问题。
- 医生回复后，患者可在自己的问题列表中看到回复结果。
- 刷新页面后，医生和患者登录态仍然保留。
- 所有核心流程通过后端 API 完成，不依赖前端本地比对密码或本地伪造业务结果。

### 3.3 In Scope

- 患者注册
- 患者登录
- 医生登录
- 医生列表查询
- 患者提交问题
- 医生查询问题列表
- 医生回复问题
- 医生标记问题已答
- 登录态本地持久化恢复
- MySQL 表结构与初始化数据首次导入
- PRD、测试与交付文档补齐

### 3.4 Out of Scope

- 医生排班管理
- 在线聊天、语音或视频问诊
- 支付、订单、处方流转
- 短信验证码、实名认证
- 复杂权限系统与后台管理系统

## 5. 用户场景

### 5.1 核心场景

1. 患者进入问诊页，完成注册或登录。
2. 患者在问诊页打开“提交问题”弹窗，选择医生并填写问题描述。
3. 系统保存问题并在患者列表中展示问题状态。
4. 医生登录自己的诊室页面，查看属于自己的待回复问题。
5. 医生填写回复内容，提交后将问题状态更新为已答。
6. 患者重新进入问诊页时，可查看医生回复结果。

## 6. 功能需求

### 6.1 功能总览

| 功能模块 | 描述 | 优先级 |
| --- | --- | --- |
| 患者认证 | 注册、登录、登录态恢复 | P0 |
| 医生认证 | 登录、登录态恢复 | P0 |
| 医生列表 | 查询医生基础信息与在线状态 | P0 |
| 问题管理 | 提问、查询、回复、标记已答 | P0 |
| 初始化数据 | 从 JSON 首次导入到 MySQL | P0 |

### 6.2 详细需求

#### 需求 1：患者注册与登录

- 目标：让患者可以通过用户名和密码进入问诊系统。
- 触发入口：前端页面 `/consultation`
- 前置条件：患者进入问诊页面。
- 业务规则：
  1. 注册时必须填写用户名和密码。
  2. `displayName` 允许为空，为空时默认使用用户名。
  3. 登录成功后系统保存患者当前会话。
- 正常流程：
  1. 患者切换到注册或登录模式。
  2. 输入用户名和密码并提交。
  3. 前端调用患者注册或登录接口。
  4. 成功后进入患者问诊中心并加载患者问题列表。
- 异常流程：
  1. 用户名已存在时，注册失败并提示。
  2. 用户名或密码错误时，登录失败并提示。
  3. 接口调用失败时，提示操作失败。
- 结果输出：前端保存 `currentPatient`，页面展示患者专属视图。

#### 需求 2：医生登录

- 目标：让医生通过后端接口完成认证并进入诊室。
- 触发入口：前端页面 `/doctor/login`
- 前置条件：医生访问登录页面。
- 业务规则：
  1. 医生登录必须调用后端接口，不允许前端直接读取医生列表做密码比对。
  2. 登录成功后返回医生基础信息。
  3. 登录成功后系统保存医生当前会话。
- 正常流程：
  1. 医生输入用户名和密码。
  2. 前端调用医生登录接口。
  3. 成功后跳转到 `/doctor/room/:username`。
- 异常流程：
  1. 用户名或密码错误时提示登录失败。
  2. 接口异常时提示服务不可用。
- 结果输出：前端保存 `currentDoctor`，诊室页展示医生专属问题列表。

#### 需求 3：患者提交问题

- 目标：让患者向指定医生发起问诊。
- 触发入口：问诊页“提交问题”按钮和弹窗。
- 前置条件：
  1. 患者已登录。
  2. 医生列表已加载成功。
- 业务规则：
  1. 患者必须选择医生。
  2. 患者必须填写问题内容。
  3. 新问题状态默认为 `pending`。
- 正常流程：
  1. 患者打开弹窗。
  2. 选择医生并填写问题。
  3. 提交后调用创建问题接口。
  4. 成功后刷新患者问题列表并关闭弹窗。
- 异常流程：
  1. 未选医生时禁止提交并提示。
  2. 问题内容为空时禁止提交并提示。
  3. 接口失败时提示提交失败。
- 结果输出：数据库新增一条问题记录，状态为待处理。

#### 需求 4：医生查看与处理问题

- 目标：让医生在诊室页面查看并处理属于自己的问题。
- 触发入口：诊室页面 `/doctor/room/:username`
- 前置条件：医生已登录。
- 业务规则：
  1. 医生只能查看分配给自己的问题。
  2. 问题分为待回复和已回复两类。
  3. 回复成功后问题状态变为 `answered`。
  4. 标记已答时，如果没有手动填写回复，系统可使用默认回复文案。
- 正常流程：
  1. 进入诊室后调用问题查询接口。
  2. 医生查看待处理问题列表。
  3. 医生填写回复并提交，或执行标记已答。
  4. 前端刷新问题列表。
- 异常流程：
  1. 未登录访问诊室时跳回登录页。
  2. 接口失败时提示刷新失败或回复失败。
- 结果输出：问题记录更新为已答，并保存答复内容和答复时间。

#### 需求 5：登录态持久化恢复

- 目标：保证用户刷新页面后仍然保持当前登录身份。
- 触发入口：前端应用初始化、页面刷新后重载。
- 前置条件：本地已有上一次成功登录的医生或患者信息。
- 业务规则：
  1. 医生与患者的本地缓存键分开存储。
  2. 恢复会话后需要自动拉取对应问题列表。
  3. 登出时必须清空本地缓存。
- 正常流程：
  1. 应用启动时读取本地缓存。
  2. 若存在患者缓存，恢复患者会话并加载患者问题。
  3. 若存在医生缓存，恢复医生会话并加载医生问题。
- 异常流程：
  1. 本地缓存损坏时忽略缓存并回到未登录状态。
- 结果输出：医生和患者刷新页面后仍可直接继续操作。

#### 需求 6：初始化数据首次导入

- 目标：将前端 `src/data` 下的 JSON 初始化数据导入 MySQL。
- 触发入口：后端服务首次启动，且目标表为空。
- 前置条件：数据库可用，JSON 文件可定位。
- 业务规则：
  1. 仅在目标表为空时执行导入。
  2. 一旦表中已有数据，后续重启不重复导入。
  3. 需支持从当前工作目录向上查找项目根目录，避免固定相对路径导致找不到文件。
- 正常流程：
  1. 服务启动。
  2. 检查目标表是否为空。
  3. 若为空，读取 JSON 并插入数据库。
- 异常流程：
  1. JSON 路径未找到时启动失败并输出明确日志。
  2. JSON 格式错误时启动失败并输出明确日志。
- 结果输出：`doctors`、`patient_users`、`questions` 初始化完成。

## 7. 交互与页面要求

### 7.1 页面/入口

| 页面/入口 | 改动说明 |
| --- | --- |
| `/` | 首页展示项目入口与医生统计信息 |
| `/doctors` | 医生列表展示基础信息与在线状态 |
| `/consultation` | 患者登录、注册、提问、查看问题列表 |
| `/doctor/login` | 医生账号登录 |
| `/doctor/room/:username` | 医生查看与处理问题 |

### 7.2 交互要求

- 患者登录和注册在同一页面切换，不跳转到独立页面。
- 患者提交问题使用弹窗承载，弹窗需支持医生选择和问题输入。
- 医生选择组件在选中后，头像、姓名、科室信息必须完整显示，不能裁切。
- 医生诊室页需显式区分待回复问题和已回复问题。
- 登录成功、提问成功、回复成功均需有明确反馈。
- 登录失败、接口失败、表单校验失败均需有明确错误提示。
- 刷新页面后，若存在本地登录态，页面应自动恢复到对应身份视图。

### 7.3 文案要求

- 登录成功、注册成功、问题提交成功、回复成功需要有成功提示。
- 用户名或密码错误、未选择医生、问题内容为空需要有明确提示。
- 无数据时需显示空状态文案，例如“暂无问诊记录”“暂无待处理问题”。

### 8.2 数据库要求

- 使用 MySQL 作为运行数据库。
- 使用 MyBatis-Plus 作为数据访问框架。
- 初始化数据来源：
  - `web/qa-web/src/data/doctor-user-list.json`
  - `web/qa-web/src/data/patient-user.json`
  - `web/qa-web/src/data/question-list.json`
- 初始化策略：仅在对应表为空时导入一次。
- 导入后数据库为系统运行时唯一真实数据源。

### 8.3 接口要求

| 接口 | 方法 | 请求参数 | 返回结果 | 说明 |
| --- | --- | --- | --- | --- |
| `/api/doctors` | GET | `activeOnly` | 医生列表 | 查询医生信息 |
| `/api/doctors/login` | POST | `username`, `password` | 医生信息 | 医生登录 |
| `/api/patients/register` | POST | `username`, `password`, `displayName` | 患者信息 | 患者注册 |
| `/api/patients/login` | POST | `username`, `password` | 患者信息 | 患者登录 |
| `/api/questions` | GET | `doctorId` / `patientId` / `status` | 问题列表 | 查询问题 |

| `/api/questions/{id}/mark-answered` | POST | 无 | 更新后的问题 | 标记已答 |

### 8.4 联调说明

- 前端患者认证、医生认证依赖 `qa-service-user`。
- 前端问题查询、创建、回复、标记依赖 `qa-service-question`。
- 前端开发端口需避开 `8080` 和 `8081`。
- 页面刷新后的状态恢复依赖前端本地缓存和重新拉取问题接口。

## 9. 非功能需求

### 9.1 性能

- 医生列表与问题列表接口在本地开发环境下应快速响应，不出现明显卡顿。
- 患者提交问题和医生回复问题后，列表状态应立即可见。

### 9.2 安全

- 医生和患者密码认证必须通过后端接口完成。
- 医生列表接口不应向前端返回敏感密码字段。
- 患者仅能查看自己的问题，医生仅能查看分配给自己的问题。

### 9.3 可观测性

- 后端需输出 MyBatis-Plus SQL 日志，便于开发联调。
- 启动失败时需从日志中快速定位数据库连接、初始化数据、JSON 路径等问题。
- 前端接口异常需给出明确错误反馈。

## 11. 风险与依赖

### 11.1 风险项

## 12. 拆分步骤

本需求涉及前端页面、两个后端服务、数据库初始化和联调，必须拆分实施。

### 12.1 拆分原则

- 先完成数据层和初始化能力，再完成接口层和页面接入。
- 先完成主流程，再处理刷新恢复、异常流程和样式细节。
- 每个子任务都必须能独立验证结果。

### 12.2 标准拆分步骤

1. 数据建模与初始化
   明确 `doctors`、`patient_users`、`questions` 三张表结构，以及三个 JSON 的首次导入策略。
2. 用户服务开发
   完成患者注册、患者登录、医生列表、医生登录接口。
3. 问题服务开发
   完成问题创建、查询、回复、标记已答接口。
4. 前端患者流程接入
   完成患者登录注册页、提问弹窗、患者问题列表、接口联调。
5. 前端医生流程接入
   完成医生登录页、诊室问题列表、回复和标记已答交互。
6. 会话恢复与体验修正
   完成刷新恢复、空状态、错误提示、关键样式修复。
7. 测试与文档交付
   完成接口测试、手工回归、PRD 和测试文档补齐。
