## 📖 第二部分：完整业务上下文

### 2.1 业务背景与价值

#### 2.1.1 业务痛点
目前患者无法通过用户名密码直接登录系统，只能通过医生代为操作，导致：
1. 患者体验差，等待时间长
2. 医生工作负担重
3. 无法实现患者自主管理健康档案
4. 缺乏独立的身份认证机制

#### 2.1.2 业务价值
- **用户体验**: 提升患者自主访问系统的便利性
- **效率提升**: 减少医生协助登录的时间成本
- **商业价值**: 增强患者对平台的粘性和满意度

### 2.2 用户画像与场景

#### 2.2.1 目标用户
| 用户类型 | 特征描述 | 使用频率 | 技术水平 |
|---------|---------|---------|---------|
| 患者用户 | 需要访问个人健康信息的普通用户 | 高频 | 中 |
| 管理员 | 系统管理人员 | 低频 | 高 |

#### 2.2.2 典型使用场景

**场景 1: 患者正常登录**
- **触发条件**: 患者希望访问个人健康信息
- **用户目标**: 成功登录系统查看个人信息
- **操作流程**: 
  1. 打开登录页面
  2. 输入用户名和密码
  3. 点击登录按钮
  4. 系统验证凭据
  5. 登录成功后跳转到主页
- **成功标准**: 用户成功进入系统并看到个性化内容
- **异常处理**: 显示错误消息，允许重新尝试

**场景 2: 登录失败处理**
- **触发条件**: 用户名或密码错误
- **用户目标**: 了解失败原因并修正
- **操作流程**: 
  1. 输入错误的用户名或密码
  2. 系统返回错误提示
  3. 用户修正输入后重试
- **成功标准**: 用户理解错误原因并能正确操作
- **异常处理**: 限制连续失败次数，防止暴力破解

### 3.4 API 接口设计

#### 3.4.1 接口列表

**接口 1: 患者登录**

- **URL**: `POST /api/v1/patients/login`
- **描述**: 患者用户使用用户名和密码进行登录
- **认证**: 不需要
- **请求头**:
  ```
  Content-Type: application/json
  ```

- **请求体**:
  ```json
  {
    "username": "string",
    "password": "string"
  }
  ```

- **请求参数说明**:
  | 参数名 | 类型 | 必填 | 说明 | 校验规则 |
  |-------|------|------|------|---------|
  | `username` | String | 是 | 用户名 | 长度 3-50，只能包含字母、数字、下划线 |
  | `password` | String | 是 | 密码 | 长度 8-128，必须包含字母和数字 |

- **成功响应 (200)**:
  ```json
  {
    "code": 200,
    "message": "登录成功",
    "data": {
      "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
      "expiresIn": 7200,
      "user": {
        "id": 1,
        "username": "john_doe",
        "email": "john@example.com"
      }
    }
  }
  ```

- **错误响应**:
  | HTTP 状态码 | 错误码 | 说明 |
  |------------|-------|------|
  | 400 | VALIDATION_ERROR | 参数校验失败 |
  | 401 | INVALID_CREDENTIALS | 用户名或密码错误 |
  | 423 | ACCOUNT_LOCKED | 账户已被锁定 |
  | 500 | INTERNAL_ERROR | 服务器内部错误 |

- **业务逻辑**:
  1. 验证请求参数格式
  2. 查询数据库中是否存在该用户名
  3. 检查账户是否被锁定
  4. 验证密码是否正确
  5. 如果验证失败，增加失败计数并可能锁定账户
  6. 如果验证成功，重置失败计数并生成JWT Token
  7. 返回Token和用户信息

**接口 2: 获取当前用户信息**

- **URL**: `GET /api/v1/patients/me`
- **描述**: 获取当前登录患者的信息
- **认证**: 需要 JWT Token
- **请求头**:
  ```
  Authorization: Bearer <token>
  ```

- **成功响应 (200)**:
  ```json
  {
    "code": 200,
    "message": "success",
    "data": {
      "id": 1,
      "username": "john_doe",
      "email": "john@example.com",
      "phone": "+8613800138000"
    }
  }
  ```

### 4.3 常见陷阱与注意事项

#### ⚠️ 后端开发陷阱
1. **N+1 查询问题**: 使用 `@EntityGraph` 或 JOIN FETCH
2. **事务边界**: 避免在循环中提交事务
3. **空指针异常**: 使用 `Optional` 和 null 检查
4. **SQL 注入**: 永远不要拼接 SQL，使用参数化查询

#### ⚠️ 前端开发陷阱
1. **内存泄漏**: 在 `onUnmounted` 中清理事件监听器和定时器
2. **竞态条件**: API 请求取消前一个请求
3. **状态同步**: 确保 Store 状态与 UI 同步
4. **TypeScript any**: 避免使用 `any`，定义明确类型

#### ⚠️ 大模型特有问题
1. **上下文长度**: 如果代码过长，分多次生成
2. **一致性检查**: 生成的代码要与现有代码风格一致
3. **依赖版本**: 确认使用的库版本与项目一致
4. **配置同步**: 确保新代码的配置已添加到配置文件
