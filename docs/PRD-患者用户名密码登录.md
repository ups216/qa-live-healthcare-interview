## 2. 背景与问题陈述

- **业务背景**：在线问诊场景中，患者进入「问诊」页面前需完成身份识别。当前实现依赖 **姓名 + 生日** 的弱验证方式，与常见账号体系不一致，且难以与后续权限、审计、多端会话对齐。
- **当前痛点**：
  - 身份凭证辨识度低，同名同生日易混淆（演示环境虽可「任意创建」，但产品形态不贴近真实业务）。
  - 无法与标准 **用户名 + 密码** 的注册/登录、找回密码、风控等能力扩展衔接。
  - 医生端已具备用户名密码登录心智，患者端不一致，增加理解与测试成本。
- **不做会怎样**：后续若要做服务端账号体系、会话与合规审计，需推翻现有弱验证逻辑，返工成本高。

---

## 3. 目标与成功指标

- **定性目标**
  1. 患者使用 **用户名 + 密码** 完成登录；新用户可通过 **注册** 创建账号（含必要资料字段，见数据模型）。
  2. 登录成功后，问诊页行为（展示患者信息、提问记录等）与现有一致或明确升级说明。
  3. 整体交互与医生登录页风格协调（表单、校验、错误提示）。
- **定量指标（可选）**
  - 登录/注册主路径操作在常规网络下 **3 秒内** 完成可感知的反馈（前端本地或接口返回）；具体数值可在联调后写入基线。
- **非目标（Out of scope）**
  - 手机号验证码登录、微信一键登录、人脸识别。
  - 生产级密码找回（邮件/短信）全流程（可作为后续 PRD）。
  - 医疗数据分级与完整等保条款（本需求仅做产品与接口层约定，合规以法务/安全为准）。

| 后端（分期） | 见第 11 章 **阶段 B/C**：患者账号表、注册/登录 API、密码存储策略、会话与 token（若采用 JWT 等）。 |

- 管理后台对患者账号的封禁、重置密码（可单列需求）。

### 4.3 依赖与前置条件

- **阶段 A**：无强依赖后端，可使用静态数据或内存状态完成演示（与现有 `patient-user.json` / store 模式一致时需改模型）。
- **阶段 B/C**：MySQL 已可用（如 `docker-compose`）、`qa-service-user` 或独立患者服务可扩展；与现有医生接口风格（REST、错误体）保持一致便于前端统一封装。

## 5. 用户与场景

### 5.1 角色

| 角色 | 描述 | 主要诉求 |

| 患者（问诊用户） | 使用在线问诊提交问题、查看回复 | 用熟悉的账号密码注册/登录，安全进入问诊主页 |
| 医生 | 在诊室查看患者提问 | 仍能看到可信的患者标识（姓名等），不强制本 PRD 改医生端（除非患者展示字段变化） |

### 5.2 用户故事（可验收）

| ID | 用户故事 | 优先级 |
|----|----------|--------|
| US-01 | 作为患者，我希望用 **用户名和密码** 登录，以便进入我的问诊主页 | P0 |
| US-02 | 作为新患者，我希望 **注册** 账号并设置密码，以便首次使用问诊服务 | P0 |

| US-04 | 作为患者，我希望 **退出登录** 后无法访问需登录态的问诊内容，以便在共享设备上保护隐私 | P1 |
| US-05 | 作为患者，我希望登录态在 **刷新页面** 后仍保持（可选，建议阶段 B 用 token + 存储实现），以便体验连贯 | P1 |

## 6. 交互与流程

### 6.1 主流程

**登录**

1. 用户进入问诊页（如 `/consultation`），未登录时展示登录区域。
2. 输入用户名、密码，点击登录。
3. 校验通过 → 进入「患者问诊主页」（展示称呼、问题列表等，与现有一致）。
4. 校验失败 → 展示统一错误文案（见第 9 章）。

**注册**

1. 用户切换到「注册」页签（或独立注册入口，产品二选一，建议页签减少跳转）。
2. 输入用户名、密码、确认密码；必填展示姓名（用于医生端展示）；可选：生日、手机、性别等。
3. 提交 → 用户名唯一则创建账号并自动登录；否则提示「用户名已被占用」。

### 6.2 分支与异常流程

| 场景 | 预期行为 |
|------|----------|
| 用户名为空 / 格式不合法 | 前端拦截，表单项错误提示 |
| 密码过短或不符合策略 | 前端拦截；后端再次校验并返回 400 + 业务码 |
| 登录失败（密码错误 / 用户不存在） | **统一文案**：如「用户名或密码错误」，避免枚举用户 |
| 网络超时 | Toast/Alert：请检查网络后重试 |
| 注册重复用户名 | 明确提示「该用户名已被注册」 |
| 阶段 A 仅前端 | 无网络；失败原因仅限本地校验 |

### 6.3 线框 / 原型（可选）

- 对齐 `DoctorLogin.vue`：垂直表单、大号输入、密码框、主按钮全宽。
- 问诊页登录区：建议 **登录 | 注册** 页签 + 底部测试账号说明（演示环境）。

## 7. 数据模型

### 7.1 实体与关系

- **Patient（患者）**：与 **Question（问诊问题）** 为一对多：一个问题归属一名患者。
- 阶段 A：患者列表可为前端 JSON / 内存；阶段 B：`patients` 表持久化。

### 7.2 字段说明

**患者（逻辑模型，前后端对齐）**

| 实体 | 字段 | 类型 | 必填 | 说明 / 校验 |
|------|------|------|------|-------------|
| Patient | id | string | 是 | 全局唯一，后端生成 UUID 或雪花 |
| Patient | username | string | 是 | 唯一；长度 3～32；字符集建议字母数字下划线（产品可扩展中文用户名，需额外约定） |
| Patient | password | — | 是 | **阶段 A**：可演示明文；**阶段 B**：仅存 **哈希**（如 BCrypt），禁止落库明文 |
| Patient | name | string | 是 | 展示名，用于医生端与问题列表 |
| Patient | birthday | string | 否 | `YYYY-MM-DD`，可选 |
| Patient | phone | string | 否 | 脱敏展示 |
| Patient | gender | string | 否 | 枚举或文本 |

### 7.3 数据迁移与兼容

- 若存在历史「姓名 + 生日」种子用户：可 **一次性脚本** 生成默认 `username`（如拼音）与临时密码策略，或标记为仅演示数据重建；需在实施阶段定稿。
- 问诊 JSON/API 中 `patientId`、`patientName` 与新的 `Patient.id`、`Patient.name` 保持一致映射。

## 8. 接口约定

### 8.1 阶段 A（仅前端）

- **N/A**：无 HTTP 接口；登录/注册逻辑在 store + 本地数据源完成。

### 8.2 阶段 B/C（后端）

| 方法 | 路径（示例） | 说明 | 鉴权 |
|------|----------------|------|------|
| POST | `/api/patients/register` | 注册 | 无 |
| POST | `/api/patients/login` | 登录，返回 token（及过期时间） | 无 |
| POST | `/api/patients/logout` | 注销会话（若服务端会话） | Bearer |
| GET | `/api/patients/me` | 当前患者信息 | Bearer |

### 8.3 请求 / 响应示例（约定级）

**登录响应（示例）**

```json
{
  "token": "<jwt-or-opaque>",
  "expiresIn": 3600,
  "patient": {
    "id": "patient001",
    "username": "zhaoming",
    "name": "赵明"
  }
}
```

**错误体（约定）**

```json
{
  "code": "AUTH_INVALID_CREDENTIALS",
  "message": "用户名或密码错误"
}
```

（具体字段名与现有 `ErrorResponse` 对齐。）

## 9. 异常、边界与安全

- **业务规则边界**：用户名唯一；密码最小长度 ≥ 6（可配置）；注册时确认密码须一致。
- **异常场景**：401 未登录访问受保护资源 → 跳转登录或展示登录框；403 与 401 语义区分按后端规范。
- **安全与隐私**
  - 生产环境 **禁止** 在日志中打印密码与 token 全文。
  - 登录失败响应 **不区分**「用户不存在」与「密码错误」（对外文案统一）。
  - 密码存储使用单向哈希 + 盐（后端阶段强制）。
- **性能与限流（可选）**：登录接口建议限流（如 IP + 用户名维度），防暴力破解；数值由运维与安全定。

## 10. 验收标准（总览）

| ID | 验收项 | 验收方式 |
|----|--------|----------|
| AC-01 | 新用户可完成注册，用户名重复时不可注册并有提示 | 手工 |
| AC-02 | 已存在用户可用正确密码登录并进入问诊主页 | 手工 |
| AC-03 | 错误密码或错误用户名登录失败，提示为统一文案，不暴露用户是否存在 | 手工 + 可选接口测试 |
| AC-04 | 退出后问诊主页需重新登录才能访问（阶段 A：内存清空；阶段 B：清除 token） | 手工 |
| AC-05 | 提交的问题仍关联正确的 `patientId` 与展示名 | 手工 / 回归 |

## 11. 拆分步骤与里程碑（分阶段验收）

采用 **先前端闭环、再后端账号体系与会话** 的拆分，降低联调阻塞。每阶段有独立 **交付物** 与 **阶段验收**。

### 阶段 A：前端登录 / 注册（本地 store + 静态或内存数据）

| 项目 | 内容 |
|------|------|
| **交付物** | 问诊页替换为「用户名 + 密码」登录与注册表单；`Patient` 模型含 `username` / `password`（演示可明文）；`loginPatient` / `registerPatient`；登录态 `currentPatient`；退出登录；种子数据更新 |
| **阶段验收** | ① 使用种子账号可登录并看到问诊主页；② 新注册用户可登录且问题提交关联新 `patientId`；③ 错误密码提示统一；④ 退出后需重新登录；⑤ 与医生端路由/入口无回归问题 |

### 阶段 B：后端账号持久化 + 登录接口（无会话或简易 token）

| 项目 | 内容 |
|------|------|
| **交付物** | `patients` 表 DDL + 初始化脚本；注册/登录 REST API；密码 BCrypt（或项目选定算法）；登录响应含 token 占位或短期 JWT；前端改为 `fetch` 调用并保存 token |
| **阶段验收** | ① 重启服务后用户数据仍存在；② 注册/登录与数据库一致；③ 响应中无密码字段；④ 错误码与 PRD 第 8.3 节一致；⑤ 前端集成后阶段 A 验收项仍全部通过 |

### 阶段 C：会话、Token 续期与安全加固（可选合并至 B）

| 项目 | 内容 |
|------|------|
| **交付物** | Token 过期与刷新策略（若采用 JWT）；`/api/patients/me`；请求拦截器自动带 Authorization；可选 HttpOnly Cookie 方案（需另评） |
| **阶段验收** | ① 刷新页面在 token 有效期内保持登录（满足 US-05）；② 过期后提示重新登录；③ 限流或登录失败次数限制（若已实现）可通过简单脚本验证 |
