## 一、项目背景与目标

### 1.1 项目定位

本项目为 **QA 在线医疗问诊面试项目**，用于在限定时间（2 天内）内，通过 AI Coding 方式完成「编码 + 测试 + 文档」全流程，并最终以 PR 与演示形式交付。产品形态为医疗问诊平台：患者可浏览医生、进入诊室问诊，医生可登录并处理问诊。

### 1.2 本次需求目标

在现有前端（Vue 3 + 本地 JSON 数据）与后端（qa-service-user 仅有 CORS 测试接口）基础上，完成以下交付：

1. **首页国际化**：首页支持中/英文切换，提升可访问性。
2. **医生数据后端化**：医生数据从 JSON 迁移至 MySQL，并通过 qa-service-user 提供 API，为后续扩展与联调打基础。
3. **前后端联调**：医生列表页从后端 API 获取数据并正确展示。
4. **可复现的测试与文档**：提供 API 的 curl 测试脚本、API_TEST.md 及 docs/api.md，便于验收与维护。

| 角色 | 描述 | 与本需求相关场景 |

## 三、功能需求详述

### 3.1 需求一：首页中英文切换

| 项目 | 说明 |
|------|------|
| **需求描述** | 在 Web 端首页提供中英文切换能力，用户选择语言后首页内容动态切换为对应语言。 |
| **用户故事** | 作为访客，我希望在首页右上角通过下拉选择「中文」或「English」，以便用自己熟悉的语言浏览平台介绍。 |
| **范围** | 仅针对 **首页**（路由 `/`，组件 `Home.vue`），其他页面（如医生列表、关于、诊室等）不要求在本需求中做多语言。 |
| **交互要求** | 在页面 **右上角** 提供语言切换下拉菜单，选项为 **中文** / **English**，选择后 **动态切换** 首页所有需展示的文案，无需刷新整页。若语言切换控件放在公共 Header 中，则在首页展示时该控件须位于页面右上角区域（与 README「右上角」一致）。 |
| **数据与规范** | 中英文文案以语言资源文件形式维护，资源文件存放在 **`web/qa-web/src/locales`** 目录中（如 `zh-CN.ts`/`en.ts` 或同类结构）。 |
| **首页需国际化的内容** | 标题、副标题、特性列表（专业医生团队、实时在线问诊、隐私安全保护）、按钮文案（立即问诊、查看医生）、统计区块标签（专业医生、问题总数、待响应问题、在线诊室）、开放诊室区块标题与副标题、诊室卡片内按钮「进入诊室」等所有首页可见文案。 |
| **首页数据依赖** | 首页存在「统计」与「开放诊室」区块，当前依赖 store 中的医生与问诊数据。实现医生数据 API 化后，需保证首页在展示时能获得医生数据（例如在进入首页或应用时请求医生列表 API 并写入 store，或首页单独请求），以便统计与开放诊室区块数据正确，不出现空白或错误。 |

**验收标准（AC）**：

- AC1.1：首页右上角存在语言切换控件，可识别为下拉或选择器。
- AC1.2：下拉选项包含「中文」「English」两种。
- AC1.3：选择「中文」时，首页所有上述文案显示为中文。
- AC1.4：选择「English」时，首页所有上述文案显示为英文。
- AC1.5：语言资源文件位于 `web/qa-web/src/locales` 目录下。
- AC1.6：切换语言时仅首页内容变化，不要求其他页面同步切换。
- AC1.7：首页「统计」与「开放诊室」区块在医生数据可从 API 获取的前提下，数据正确展示（数字与列表与数据源一致），不因医生数据改为 API 而出现长期空白或错误。

### 3.2 需求二：医生数据存储与 API

| 项目 | 说明 |
|------|------|
| **需求描述** | 将医生相关数据从前端 JSON 迁移至 MySQL，并通过 qa-service-user 提供可被前端医生页面使用的 API。 |
| **用户故事** | 作为平台，希望医生数据由数据库统一管理并通过 API 对外提供，以便前端医生列表页从服务端获取实时、可扩展的医生信息。 |
| **子需求 2.1：基础设施** | 在 **项目根目录** 创建 **docker-compose.yml**，用于启动 MySQL 数据库，并挂接 **phpMyAdmin** 作为数据库管理界面，便于查看与维护数据。README 未指定文件路径时，以项目根目录为准。 |
| **子需求 2.2：后端 API** | 在 **qa-service-user** 服务中创建 **支持前端医生页面（Doctors.vue）显示医生列表** 所需的 API。即：至少提供「医生列表」接口，返回字段需满足 Doctors.vue 与 store 中 Doctor 模型的展示与使用需求（如 id、username、name、title、department、avatar、experience、specialties、isActive 等）。 |
| **子需求 2.3：数据迁移** | 当前 `web/qa-web/src/data/doctor-user-list.json` 中的医生数据需迁移至 MySQL，并可通过上述 API 查询到，保证前端展示与原有逻辑一致（可含密码字段但不通过列表 API 暴露给前端）。 |

**验收标准（AC）**：

- AC2.1：**项目根目录** 存在 **docker-compose.yml**，可一键启动 MySQL 与 phpMyAdmin。
- AC2.2：通过 phpMyAdmin 或命令行可访问 MySQL，并存在存储医生信息的表及数据。
- AC2.3：qa-service-user 提供 **医生列表 API**（如 `GET /api/doctors` 或等价路径），返回 JSON 数组，结构与前端 Doctor 模型兼容。
- AC2.4：API 返回数据包含前端医生列表页展示所需字段（id、username、name、title、department、avatar、experience、specialties、isActive 等），且至少包含与当前 `doctor-user-list.json` **等价** 的医生数据：即字段含义与展示逻辑一致、条数不少于 5 条（可为相同 5 条或业务等价数据）。

---

### 3.3 需求三：前后端联调（医生列表）

| 项目 | 说明 |
|------|------|
| **需求描述** | 前端医生列表页（Doctors.vue）改为从 qa-service-user 的医生列表 API 获取数据并展示，完成从「静态 JSON」到「后端 API」的联调。 |
| **用户故事** | 作为访客，我打开「医生」页面时，看到的医生列表来自后端服务，数据与数据库一致，且列表可正常展示头像、姓名、科室、专长、在线状态及「进入诊室」等交互。 |
| **技术要求** | 前端需调用 qa-service-user 的医生列表接口；考虑 CORS、网络与错误处理（如 API 不可用时的提示或降级策略可由实现决定）。 |

**验收标准（AC）**：

- AC3.1：在 qa-service-user 与前端同时运行、且后端已连接 MySQL 并具备医生数据的前提下，打开前端「医生」页面，列表数据来自该 API，而非本地 JSON。
- AC3.2：医生列表页展示的医生信息（姓名、职称、科室、专长、在线状态等）与 API 返回一致，且「进入诊室」等既有交互仍可用。
- AC3.3：前后端联调通过（无 CORS 阻塞、接口路径与数据格式一致）。
- AC3.4：当医生列表 API 返回非 2xx（如 500、网络错误）或返回空数组时，医生列表页不崩溃，且有可识别的反馈：如「加载失败」「暂无医生」等文案或占位展示，具体形式可由实现决定。

## 四、测试与文档需求（交付物）

### 4.1 测试相关

| 项目 | 说明 |
|------|------|
| **测试脚本** | 使用 **curl** 编写针对「医生列表页所使用 API」的测试用例脚本，放在 **`scripts/`** 目录下，便于重复执行与自动化验收。脚本应在常见环境（如 macOS/Linux 或 Git Bash）下可执行，并在 API_TEST.md 中说明执行方式（如 `bash scripts/xxx.sh`）。 |
| **API 测试说明** | 提供 **API_TEST.md**。README 未指定路径时，**统一放在项目根目录**，便于与 README 对照。内容需说明上述 API 测试的 **执行方式**（环境准备、如何运行 curl 脚本、预期结果、可选的手动 curl 示例）。 |

**验收标准（AC）**：

- AC4.1：存在可执行的 curl 测试脚本，覆盖医生列表 API（如 GET 列表、必要时包含状态码与关键字段校验说明）。
- AC4.2：存在 API_TEST.md，阅读后能理解如何执行上述 API 测试并核对结果。

### 4.2 文档相关

| 项目 | 说明 |
|------|------|
| **API 文档** | 生成 **`/docs/api.md`**，对 **qa-service-user 服务中的所有 API** 进行说明（至少包含医生列表 API 及现有测试用 CORS 接口），便于开发与测试参考。README 要求「对所有 api 测试进行说明」，故文档中应包含：每个 API 的请求方法、路径、参数、响应示例；以及对各 API 如何测试的说明（可引用 API_TEST.md 或内联简要步骤）。 |

**验收标准（AC）**：

- AC4.3：存在 **`docs/api.md`**，内容包含 qa-service-user 的 **全部** 对外 API（含 GET /api/doctors 与 /api/test/cors 的 GET/POST/OPTIONS 等），每项具备：请求方法、路径、参数、响应示例或说明；以及对各 API 的测试说明（或引用 API_TEST.md）。

- 生产级安全、性能、权限与部署方案（面试场景以功能与可验收性为主）。
